# Creating a world

How a world of Heimstrecke is made, from the first idea to a `.world` package, and what the project learned on the way. State of 2026-10-23, written from the code and the sessions that built it. Constants are quoted with their name so they can be found with `grep`; if code and this page disagree, the code is right and this page needs a fix. Commands and make targets are listed in [reference.md](./reference.md), the licence side is in [licences.md](./licences.md).

## What a world is

A world is a **recipe** in git (`./worlds/<id>/`) plus a **build** outside git (`./data/out/worlds/<id>/`). The build is a square of 1 km glTF tiles (10 km by 10 km = 100 tiles by default), a coarse horizon ring, a manifest `world.json` and a metrics report. `pack.py` turns a build into one shareable file, `<id>-<version>.world` (a ZIP with the manifest first). Nothing in the game is specific to a world: a new world is a new recipe directory and no code.

```
worlds/<id>/world.json          recipe (required)
worlds/<id>/starts.json         start points of the drive menu (optional)
worlds/<id>/route.json          an OSRM route response (optional)
worlds/<id>/smoke.json          tunnel and bridge test runs (optional)
worlds/<id>/scenes.json         camera scenes for screenshots (optional)
worlds/<id>/clipping_baseline.json   ratchet baseline of the clipping report (optional)
```

## Step by step

1. **Pick the area.** Look up the town centre (Nominatim is fine for a one-off lookup, do not store its results) and decide the playable square. 10 km is the tested size; much more is built on a developer machine, because the build holds the whole area in memory. DGM1 covers Baden-Württemberg only; a world in France takes the IGN LiDAR HD (`"terrain": "lidarhd"`, see [Worlds outside Baden-Württemberg](#worlds-outside-baden-württemberg)), elsewhere the global GEDTM30 (`"terrain": "gedtm30"`, about 30 m, a substitute raster; see [Terrain sources outside Germany and France](#terrain-sources-outside-germany-and-france)). Outside UTM zone 32 the recipe names the zone in `epsg`.
2. **Write the recipe** `worlds/<id>/world.json` (schema 1, checked by `pipeline/world.py`, `RecipeError` ends the build with exit code 2). Keys: `id` (`[a-z0-9-]+`), `name`, `version` (string such as `"1"` or `"0.1.0"`, a bare number is rejected), `min_game` (same format), `center` as `[lat, lon]`, `size_km`, `horizon_km` (40 in all worlds), `bbox` as `[west, south, east, north]` of the OSM extract, `osm_region` (Geofabrik path), `route` and `starts` (file names, optional), `terrain` (`dgm1`, `lidarhd` or `gedtm30`), `biome` (`temperate`, `mediterranean` or `mediterranean-dry`), `width_km` and `heading_deg` (a turned rectangle), `epsg` (the UTM north zone of frame and terrain raster, default 25832; all five optional), `tracks` (tracktypes of drivable forest and field tracks, optional, see [Tracks](#tracks)), `sources` and `attribution`. Copy `sources` and `attribution` verbatim from an existing world.
3. **Choose the bbox generously.** Centre ± 0.075° longitude and ± 0.05° latitude covers a 10 km square at the latitude of Baden-Württemberg with margin. The extract depends on the recipe, so every recipe edit re-runs the extract (about 40 s).
4. **Check the derived values**: `uv run python pipeline/world.py vars worlds/<id>/world.json` prints what the Makefile derives (Copernicus tiles, DGM1 file name, Geofabrik file and URL). Do this before downloading anything.
5. **Build**: `make world W=<id>` downloads what is missing (DGM1 about 450 MB for 10 km, Copernicus 30 m tiles about 45 MB each, the regional PBF if it is not there yet), cuts the extract, and builds. Run it as `nice -n 19` on a shared machine; extract about 40 s, build about 20 to 60 s.
6. **Read the build output.** The four hard gates must say `PASS` (below). `metrics.json` and `metrics.md` in the output directory carry the details.
7. **Add start points** (`starts.json`): list the named roads near the centre from the extract (`extract.pkl` holds the roads with their tags) and take the midpoint of an edge, so the start lies on the road. See [Start points](#start-points).
8. **Look at it.** `make fly` and `make drive` with `--world`, or software renders (`make render`, see the reference). A world that builds is not a world that drives: nothing replaces driving the start points once.
9. **Add a route** if the world has one (an OSRM response in `route.json`; over forest tracks use `tools/route_from_extract.py`, see [Tracks](#tracks)). It is optional; a world without a route builds, packs and runs, and the smoke test only checks the start points.
10. **Create the baselines**: the clipping ratchet is `SKIPPED` without `clipping_baseline.json`, and the smoke test has no timing reference without `godot/tests/reference_<id>.json` (`SMOKE_WRITE_REFERENCE=1`). Both are made from an unchanged build, not from a branch under test.
11. **Pack**: `make pack W=<id>` writes `data/out/packages/<id>-<version>.world` and refuses more than 500 MB.

## Data sources and their quirks

| Source | Used for | What to know |
|---|---|---|
| OpenStreetMap via a Geofabrik regional extract | roads, land cover, buildings, trees | One PBF per region (`stuttgart-regbez` covers Stuttgart, Berglen, Crailsheim); a world outside it needs its own PBF. `extract.py` stores the roads with their node ids (a graph needs shared nodes) and the tags listed in `ROAD_TAGS`; the pickle records the tag list and `build.py` exits with code 2 on an old pickle, `make world` then re-extracts. |
| DGM1, LGL Baden-Württemberg, 1 m | ground, road heights, route, car placement | Delivered as 2 km zips (odd easting, even northing in km), `.xyz` text with cell centres at `.50`. `fetch.py` merges them into one GeoTIFF (`dgm1_<E0>_<N0>_<km>.tif`, 12000 × 12000 float32, about 224 MB) and **deletes the zips**, so there is no per-tile cache; keep the GeoTIFF. The LGL server has been unreachable for 30+ minutes once; copy the GeoTIFF from another machine then. It is a terrain model: **no bridges, no buildings**, which explains most "steep ramp" artefacts at bridge ends. The 12 km box is the 10 km area plus `MARGIN_M` (100 m). |
| IGN LiDAR HD (MNT), 1 m | ground in France (`terrain: lidarhd`) | Raw float32 GeoTIFF from the Géoplateforme WMS (`WMS_LAYER`) in 4 km blocks (`BLOCK_M`) in Lambert-93, cached under `data/raw/lidarhd/blocks/` (64 MB each), warped bilinearly onto the 1 m EPSG:25832 grid. Corsica was covered when checked (2026-10-23, Bavella col 1218 m measured right). The service marks the sea with -9999 and **resamples it into neighbouring cells** (-9420 seen at the coast), so everything below `NODATA_BELOW_M` (-5 m) is no data. The warp of a turned raster takes about 8 minutes even with all blocks cached. |
| GEDTM30 v1.2 (OpenGeoHub), about 30 m | ground where no open 1 m model exists (`terrain: gedtm30`, Cyprus) | A terrain model, not a surface model, fused from Copernicus, AW3D30 and others by machine learning. `fetch.py` reads a window of the global cloud-optimised GeoTIFF (`GEDTM30_URL`, no API key), caches it in lon/lat under `data/raw/gedtm30/src/` and warps it bilinearly onto the 1 m UTM grid like LiDAR HD. The file carries `scale 0.1`, but the values are **metres**: at Ayia Napa Copernicus minus GEDTM30 is +0.28 m in the median (p10 -0.5, p90 +1.2 m), so the scale is not applied. The sea is no data (3.4e38, read as NaN) and is filled from the coastline. A substitute raster: 30 m between samples, small dykes, cuttings and embankments are not in it. |
| OSM coastline (`natural=coastline`) | the sea | Ways, not areas: land on the left, sea on the right. `extract.py` keeps every way within `COAST_PAD_DEG` (about 2 km) of the bbox, because the terrain raster is larger than the bbox and a coastline ending inside it would leave land and sea in one piece. |
| Copernicus DEM GLO-30 | the horizon ring only | A surface model (trees, buildings): at the Stuttgart centre it reads 2.5 to 6 m too high against DGM1. Never use it for the playable area. Under the playable area the horizon ring sinks by `HORIZON_SINK_M` (400 m); the former 30 m were enough in Stuttgart, but in the steep wooded valleys of Bavella a 200 m horizon triangle from ridge to ridge lay above the road and hid it from close by. The tiles are 1° cells chosen from the **horizon** square (centre ± `horizon_km`/2 + margin), not from the playable square, otherwise cells are dropped and the horizon changes. Never judge geometry on a Copernicus substitute raster (grade, braking and tunnel checks fail on it for no good reason). |
| OSRM response | route line | Fixture `worlds/<id>/route.json`, fetched once from an OSRM server (the public demo server is flaky and has a usage policy, see licences). The route is densified to the 5 m sample step and lifted onto the drawn road surface (`ROUTE_SNAP_M` 10 m), never onto raw DGM1. |

DGM1 `nodata` cells exist at the edge of the state: the Crailsheim box has 467,000 of them (about 0.3 %), probably where Baden-Württemberg ends. The gates still pass; the edge of such a world may be flat or cut off.

OSM tag handling worth knowing: bridges and tunnels are detected from `bridge` and `tunnel`, but `layer` is unreliable (do not use it for crossings, use plan-view geometry and heights); `building_passage`, `culvert` and `covered` are ordinary ground roads; `service` roads are not in the network (except the ones linking a track, see [Tracks](#tracks)); roads with `access=private/no`, `motor_vehicle=no` or `vehicle=no/private` are excluded, tracks of a recipe's `tracks` excepted. A named street does not imply a junction node, and tunnel edges often have no name, so scenes and tests are found by geometry, not by name.

## Coordinate frame

`frame.py`: one origin at the area centre in EPSG:25832 (UTM 32N, fine for all of Baden-Württemberg and for Corsica, which lies at 8.5 to 9.6° E inside zone 32) or the UTM zone the recipe names in `epsg` (Cyprus: 32636, WGS 84 / UTM 36N, because ETRS89 / UTM 36N does not cover Cyprus); the terrain raster is written in the same zone, a file in another zone than 25832 gets `_<epsg>` in its name, and DGM1 refuses any zone but 25832. Local metres, float64 in the pipeline and float32 in the glTF vertices. Pipeline x is east and y is north; glTF and Godot get `(x, h, -y)`, so north is −Z. Heights are stored relative to `base_height` (DGM1 at the centre). float32 has about 2 mm resolution 20 km from the origin; a jitter spike at 25 km found nothing above 1 cm, so a single origin holds for the tested sizes. A world may be turned (`heading_deg`, counter-clockwise from east): local x then runs along the heading, and everything that works in local metres is unchanged; `to_utm()` is the way back for the rasters kept in UTM. With heading 0 the unturned code path runs, so the square worlds stay byte-identical. The Corte–Aléria strip reaches 20.5 km from its origin, inside the 25 km of the jitter spike; a longer corridor would need a floating origin or sections (not built).

## What the build does

Order inside `build.py` (module in brackets):

1. **Terrain** (`terrain.py`, `build.py`): a 10 m grid (`TERRAIN_STEP`) from DGM1, 101 × 101 vertices per tile.
2. **Road graph** (`roads.py`): ways are split at shared OSM nodes, every node has exactly one height, edges are sampled every 5 m (`ROAD_STEP`). The ground height is the DGM1 median in a small radius, smoothed (`SMOOTH_WINDOW` 50 m) with fixed end heights, slope-limited (`MAX_SURFACE_GRADE` 0.24). The road surface lies `ROAD_LIFT` (0.1 m) plus `RANK_LIFT` (0.03 m) per road class above the ground. Junctions (degree ≥ 3) are convex-hull surfaces at the node height; the edge ends are cut back (`cut_back`): at least the largest half width, and as far as the arm's carriageway and sidewalk clear the carriageway and sidewalk of each neighbouring arm at the junction's angle, so every sidewalk starts where the neighbour's ends and the corner piece between them is clean; capped at `CUT_MAX` (8 m), a third of the edge, and on a slope `EXTRA_RISE` (0.3 m) over the edge grade beyond the half width, because the junction surface is flat and a long cut on a hill made the road end climb a kink. Where the width changes at a degree-2 node the strip tapers over `TAPER` (30 m) so there is no step.
3. **Terrain conform** (`conform.py`): the terrain follows the road ground on the 10 m grid up to `FLAT` (15 m) past the strip edge and blends back to DGM1 over `SHOULDER` (25 m); `push_down` then lowers every corner of a triangle that lies under a road, sidewalk or junction.
4. **Structures** (`structures.py`, `tunnels.py`, `bridges.py`): see below.
5. **Verges** (`sidewalks.py`, `skirts.py`, `priority.py`): sidewalks and kerbs, skirts down to the terrain.
6. **Markings** (`markings.py`), **railways** (`rails.py`, see "Railways" below), **buildings** (`build.py`, without underground ones: `location=underground`, `tunnel=yes`, a negative layer or only negative levels, see `extract.underground`); the part of a footprint under a road whose surface is more than `UNDER_ROAD_M` (2 m) above the building's floor, a deck with walkway and parapet included, ends `BUILDING_CLEAR_M` (1 m) below the road, below the underside of a deck, and is left out when less than `MIN_PART_M` (2.5 m) remains, so no house stands up into a bridge or a raised road; a footprint with at least `UNDER_SHARE` (half) of its area under such roads is capped as a whole, so the rest of a long low structure under a viaduct does not stick out above the deck (`RoadsOver`, Stuttgart 59 buildings, one of them the 5000 m2 structure under the B 14 interchange), **trees** (`trees.py`), **road lines** (`roads.bin`, `road_names.json`), **signs** (`signs.py`, `signs.json`), **horizon** (`build.py`).
7. **Checks** (`metrics.py`, `clipping.py`), **starts** (`starts.py`), manifest `world.json`.

Tile layers (glTF node names, `LAYERS` in `build.py`): `terrain`, `roads`, `buildings`, `tunnels`, `bridges`, `markings`, `verges`, `water`, `rails`. Colours are vertex colours. Godot gives every mesh a trimesh collision except `markings` (the route chevrons and boards are runtime meshes of `route_marks.gd`), `rails` and `water`, which also has its own smooth material. Inland water (OSM lakes, ponds, riverbanks; not the sea) is a surface of its own (`water.py`): its height comes from the banks (the lowest bank within the distance to the boundary plus 18 m, a compact lake one level), 0.25 m below them, and the terrain mesh inside is carved at least 0.3 m, 1 m from 6 m off the bank, below it and takes the gravel colour; the raster stays, so roads, skirts, trees, buildings and the gates do not see the bed. Roads crossing less than 1.5 m above the water cut the surface, buffered by 1 m. Bavella has 29 water areas (0.1 km²), Stuttgart 133 (1.5 km², 21 low road crossings). Godot materials are one-sided, so every double-sided surface is emitted with both windings, with separate vertices for ceilings and tubes so that normals do not cancel.

**Rule: new geometry goes into a new layer, not into `roads`.** `metrics.shared_heights()` indexes all `roads` vertices by (x, z) to the millimetre; a deck underside or tunnel wall at the same (x, z) breaks the gate.

### Tunnels (`tunnels.py`)

Per 5 m segment the terrain is checked at the centre and at both wall lines. **Covered** (cover ≥ `COVER_MIN` 4 m at both ends): a tube with the ceiling at `min(road + CLEARANCE (5.5 m), terrain − CEILING_COVER (0.5 m))`, walls, floor and portal walls. **Slot/cutting** (terrain only partly above the road): the terrain is cut out between the wall lines and retaining walls are built. **Open** (terrain below the road): nothing is built. The terrain is cut only where it meets the cross-section, not masked wholesale; that avoids lids, holes at mask edges and flickering surfaces and leaves `ConformedTerrain` and the gates alone. Wall pieces that stand on another carriageway are dropped (`Strips.inside`), otherwise side roads inside a tunnel are blocked. The conform has a keep rule: a grid point nearer to a tunnel segment than to a conformed road keeps DGM1; without it every portal gets a 15 to 40 m trench. Known limits: a tunnel is drawn as a straight chord between its end nodes, so the middle of a long tunnel can be open to the sky; thin cover (the Planie tunnel has 4 to 5 m) turns tubes into cuttings.

### Bridges (`bridges.py`)

Bridges are found by plan-view crossing geometry. Where a bridge is more than 1 m (`GRADE_SEP`) above the road below, the deck is raised to at least `CLEAR_MIN` (4.5 m) clearance plus `DECK_DEPTH` (1.2 m), as a plateau over the lower road falling at 8 % and smoothed over 20 m; if a short bridge between fixed abutments cannot rise enough, the road below dips instead. Per segment the deck is `deck` (underside at least `GAP_MIN` 0.5 m above DGM1 at both ends, runs of at least `MIN_DECK_RUN` 15 m) or `low` (creek bridges, chords across slopes: conformed like a ground road, no deck body, no parapet, so they are not visible as bridges). A deck has walkway, parapet, outer side, underside and end faces down to the terrain. Known limit: the step between terrain and abutment is within 5 cm at only 10 of 138 abutments in Stuttgart (worst case several metres), because a road in the same 10 m cells pushes the terrain down again; end faces reach below the terrain to hide it. A finer local mesh or a cut along the abutment line would fix it (not built).

### Clipping, z-fighting, gaps

Roads, sidewalks and skirts are separate surfaces on a 10 m terrain, so they can intersect. The countermeasures, in the order the geometry is built:

- **Priority** (`priority.py`): one STRtree over all ground strip quads and junction hulls. Skirts, sidewalks and corners **yield** to carriageways; a corner ignores its own arms and its own node hull (otherwise two thirds of ordinary 4-arm junctions lose their corners). At narrow medians a ray outward per segment limits the skirt to half the gap, so nothing crosses a median centre line.
- **Skirts** (`skirts.py`): from the outer edge the skirt descends at 20° (`ANGLE`) into the terrain, at most `MAX_RUN` 3 m, and nothing rises above the edge: the former bank (0.25 m up over 1 m) read as a raised kerb on open land and was removed on 2026-10-25. Terrain really above the road cannot work on the 10 m grid with the 2 cm gate. Very steep roads still steepen into a wall.
- **Width taper** (`TAPER`): the `width_step` findings went from 1082 to 0. Everything that reads a strip width reads `net.half[s]`, not the per-edge width; if conform keeps the edge width while the strip widens, `terrain_below_roads` fails.
- **Report** (`clipping.py`): kinds `zfight`, `overlap`, `median`, `width_step`, `terrain_above`, `bank_buried`, `skirt_cross`, `dip`. It is an informational gate with a **ratchet** against `worlds/<id>/clipping_baseline.json` (slack `RATCHET_SLACK` 0.02; `SKIPPED` if the file is missing or centre and size differ). The baseline comes from an unchanged `main` build. It also writes camera views for the findings.
- **Not fixed**: strip-over-strip overlaps of equal class (equal lift, so no draw-order separation), worst at parallel carriageways that OSM draws closer than `lanes × 3.4` m.

## Gates and metrics

`metrics.HARD_GATES`, a failing gate ends the build with exit code 3:

| Gate | Meaning |
|---|---|
| `shared_heights` | at every graph node with ≥ 2 edges the exported road vertices differ by at most 5 cm |
| `terrain_below_roads` | terrain at least `MIN_CLEARANCE` (2 cm) below every strip at the centre and both edges (bridges and tunnels excluded) |
| `max_grade` | no section steeper than `MAX_GRADE` (25 %) |
| `node_heights` | node height within `NODE_DEV_MAX` (2 m) of the DGM1 estimate |

Informational: connected components (the largest should hold 99 %), the tile budget (`BUDGET_BYTES` 400 MB), the structure blocks, the route block and the clipping ratchet. Stuttgart: 945 km of road, 79,000 buildings, 100 tiles, build below one minute. Berglen: 393 km, 22,177 buildings. Crailsheim: 315 km, 19,629 buildings.

Method that kept the pipeline honest: build the unchanged `main` into a baseline directory first; a refactor must give byte-identical tiles (compare `sha256sum` of `tile_*.glb` and `horizon.glb`); two builds of the same code are byte-identical, which is how non-determinism is found; commit a refactor before the behaviour change; report deviations of more than 10 % from the expected numbers instead of accepting them.

## Worlds outside Baden-Württemberg

The Corsican worlds (`bavella`, `korsika-aleria-corte`) added four things, each switched by the recipe, so the Baden-Württemberg worlds build byte-identical tiles and tree files.

- **Terrain** `"terrain": "lidarhd"`: `fetch.py --source lidarhd` (see the data table). The Makefile passes `--source`, `--width` and `--heading` from the recipe; the GeoTIFF is `lidarhd_<E0>_<N0>_<km>.tif` for a square, `lidarhd_<E>_<N>_<L>x<W>_h<heading>.tif` for a turned world.
- **Sea** (`sea.py`): the raster square is cut along the coastlines and every piece right of the nearest coastline is sea. Terrain cells in it get at most 0 m, cells without data up to `SHORE_M` (30 m) landward of the coastline 0 m (the edge of the LiDAR data is not the shore line); cells without data farther inland stay NaN and the build stops there, as before. The sea is water land cover (blue, no trees); horizon vertices at 0 m are water and a flat sea reaches `HORIZON_SEA_M` (25 km) beyond the horizon square, corners included.
- **Biome** `"biome": "mediterranean"` (`biome.py`): drier, yellower ground and horizon, the ground darker on slopes (`GROUND_SLOPE`, up to 22 % from a rise of 0.15 to 0.6) and mottled by position (`GROUND_MOTTLE`, ±7 %) so the relief reads (also in `mediterranean-dry`), olive scrub, sand, and a warm granite grey on OSM bare rock and scree, between `ROCK_FROM_M` (1150 to 1550 m) and on slopes steeper than `ROCK_SLOPE` (0.75 to 1.2); four tree kinds (holm oak, pine with an umbrella crown, cypress, shrub for the maquis on `natural=scrub`/`heath`, and in Corsica (`MAQUIS`) also on all land without another cover below 1300 m and flatter than the rock slope, every 7 m, 1.5 to 3.5 m high with crowns 3 to 4.2 times as wide, over a dark olive ground, every `SHRUB_STEP` 8 m, own RNG); yellow ochre, peach, cream, pink and granite facades (`FACADES`) and terracotta roofs (`ROOF`), matched against Street View in Solenzara on 2026-11-04 and written as the colours shown (`srgb()`, the world material reads vertex colours as linear); hipped roofs (`PITCHED`, pitch 0.32, 0.4 m eaves, both windings) on footprints filling at least 80 % of their oriented envelope with a short side up to 16 m, flat roofs on the others and on caravans and ruins (Bavella 2097 of 2729 hipped, building triangles 45 100 to 70 152); untagged houses with two, three or four storeys by a centroid hash (`STOREYS`, 55/35/10 %, 3 m each plus 0.5 m) instead of 9 m; and lone houses outside the urban cover (fewer than `ISOLATED_NEIGHBOURS` within `ISOLATED_M`) without height tags on the ground floor only (`GROUND_FLOOR_M` 3.5 m). `extract.py` keeps rock, sand and scrub as their own cover kinds; the temperate palette has no colour for rock and sand and draws scrub as meadow, so nothing changes there.
- **Turned rectangles** `width_km`, `heading_deg`: `size_km` is the long side along the heading. Every square assumption takes the half side as a scalar or as `[hx, hy]` (`np.broadcast_to(half, 2)`): `Tiles`, the conform grid (rows along y), the road clip, trees, metrics, clipping, the bridge report. `Dgm1Raster` checks the coverage at the four turned corners and reads rotated rasters; `fetch.py` warps onto a grid along the local axes padded by `TURNED_PAD_M` (50 m; the clipping report reads terrain under road edges past the clip, which the square grids got from their km rounding) and fetches only the WMS blocks that touch the area (34 of 70 for Corte–Aléria). The heading of Corte–Aléria (-34.3°) is a line fitted through the T 50 nodes of the extract, the width (7 km) twice the largest distance of the T 50 from it plus margin. The menu map shows the strip along its own axes, the sun keeps its local direction.

Cyprus (`zypern-ayia-napa`) added the UTM zone per recipe (`epsg`), GEDTM30 as terrain and the biome `mediterranean-dry`: terra rossa on farmland, ochre ground, dry olive green and scrub, pale limestone on rock, no rock by height, the tree kinds of `mediterranean`, and whitewashed, cream, light ochre and concrete facades with flat roofs (no `ROOF`, the roof takes the facade colour). Signs in Cyprus (`signs.py`, `signs.gd`): side signs stand left of the travel direction; every destination, place and distance is a Greek line over a Latin one, looked up among the name variants of the places, so Turkish names of places in the north read as on the Republic's signs (Gazimağusa: Αμμόχωστος / Famagusta) and other Latin spellings match the closest variant (`CY_SPELLING`, Agia Napa: Ayia Napa); at most two destinations per panel; motorway and A routes green with the Greek line in yellow, B routes and all signposts and distance signs blue, others white; town signs white with a black border. Sources: [Wikipedia](https://en.wikipedia.org/wiki/Road_signs_in_Cyprus) (Greek and Latin script, left-hand traffic), [road sign colours](https://sites.google.com/site/roadnumberingsystems/home/general-information/road-sign-colours) (motorway green, yellow Greek, white Latin); blue for main roads after a comparison of European signs, not checked against the Cypriot regulations. The route (7.0 km from west of the marina along Agias Theklas and Nissi Avenue into the centre) is made with `tools/route_from_extract.py` from `route_waypoints.json`; the tool takes the metres per degree of longitude from the waypoints' latitude. 10 km, 2296 buildings, 120,000 trees and shrubs, 67 MB built, 23 MB packed.

Sizes: Bavella 16 km, 2.8 million trees and shrubs, 284 MB built; Corte–Aléria 41 × 7 km, 2.2 million, 294 MB built, 139 MB packed. The software render needs `RENDER_MEMORY=5g` for them (peak 3.7 GB), the default stays 3g. The frame rate with that many trees on a GPU is not measured yet.

## Tracks

`"tracks": ["grade1", "grade2"]` in a recipe makes the `highway=track` ways of these OSM `tracktype` values drivable roads (Berglen, Issue #2): `world.py vars` prints them as `TRACKS`, the Makefile passes `--tracks` to `extract.py`, which keeps such a track and its `tracktype` and `surface`, plus every plain `highway=service` way (no `service=*` subtype, so no car park aisle or driveway) that shares a node with a kept track and with another kept road (`links_only`): in OSM a forest track often meets the road only through such a way, at the L 1120 of Issue #2 the Königsbronnweg. Without the key no track and no service way is extracted and nothing changes; the Stuttgart tiles stayed byte-identical. In the network a track is 3 m wide (`ROAD_WIDTH`, a `width` tag wins), takes rank 0 like `service` (no other rank moves, so lifts, signs and the minimap stay as they were), gets no markings and no sidewalk, and ignores `access`, `vehicle` and `motor_vehicle`: most forest tracks are `motor_vehicle=forestry`, `agricultural` or `no`, and the recipe lists them to be driven. It is drawn in `COLORS["gravel"]` unless its surface is paved (`PAVED`; without a surface tag grade1 counts as paved, it is usually asphalt); a junction is gravel only where every arm is. Forest trees keep `TRACK_CLEAR` (1.5 m) from the track side instead of `ROAD_CLEAR`, so a forest track is a narrow lane. Gravel drives like asphalt for now: the surface is not in `roads.bin` and `car.gd` knows one grip; that is the next step.

Berglen with grade1 and grade2 (2026-10-25): 3885 → 5964 ways (82 of them linking service ways), 393 → 847 road km, 4218 → 6700 edges, 16 → 64 components (77 without the service links; the rest is not analysed, likely tracks cut at the bbox or joined through grade3 tracks or paths), 671,259 → 656,063 trees (-2.3 %), collision trunks 10,262 → 88,326 (every forest tree within `COLLIDE_M` of a track), 81 → 96 MB. All four gates pass; `ground_node_dev_max_m` rose from 0.89 to the 2.0 m cap and `max_grade_pct` stayed at 24.0, so steep tracks are held by the relaxation. The frame rate with that many collision trunks is not measured yet.

**Routes over tracks.** The public OSRM server uses a car profile that does not know `highway=track`: waypoints on forest tracks snapped 650 to 800 m away onto roads (Kirchheim, 2026-10-26). `tools/route_from_extract.py` runs Dijkstra on the world's `extract.pkl` instead (tracks included) and writes a response `build.py` reads like an OSRM one; the waypoints with a per-leg track factor (below 1 prefers tracks) are kept in `worlds/<id>/route_waypoints.json`, the output is byte-identical on a rerun. The duration in the response is a placeholder. **The route start needs a free straight**: the smoke test drives 6 s at full throttle, steers right for 1.5 s and brakes; a start in a town street with a bend after 150 m ended in a kerb at 0 km/h, and the reference then read `brake_30_0_s` 0.0, which fails every later run (`reference > 0`). Rotate the loop to start on a stretch of 450 m with at most 1 m deviation from the chord (Kirchheim: 0.0 m). The tool takes the metres per degree of longitude from the waypoints' mean latitude, so it also routes worlds far from 48.6° N; Korsika: Aléria – Corte uses it for the T 50 stage from Aléria (T 10) to Corte (44.7 km, `worlds/korsika-aleria-corte/route_waypoints.json`). Its start lies on the straight T 10 in Aléria (350 m within 1.1 m of the chord, then the junction onto the T 50); the smoke run's steer to the right ends against the roadside in the town there (`brake_30_0_s` 0.43 s instead of about 0.65 s), so the world has no `reference_korsika-aleria-corte.json` yet.

## Railways

`extract.py` keeps every way with `railway` in `RAIL_KINDS` (`rail`, `light_rail`, `tram`, `narrow_gauge`, `subway`) as `rails`, apart from the road network; a way that also carries `highway` stays a road too. `rails.py` draws the ones on the surface: `tunnel`, `covered=yes` and a negative `layer` are left out, a `bridge` gets a straight grade between the ground at its ends (DGM1 has no bridges; no deck or pier, the bed floats). The road wins: where a sample lies on a drawn ground road (`RoadArea.surface_height` in `priority.py`, strip quads and junction hulls, bridges and tunnels excluded), only the two rails are drawn, flat strips `RAIL_W` (8 cm) wide `RAIL_LIFT` (3 cm, above the 2 cm of the markings) over the road surface, so a tram line or a level crossing reads as rails let into the asphalt. Elsewhere a ballast bed stands `BED_TOP` (0.3 m) above the conformed ground, 3 m wide on top with slopes to 0.2 m below the ground, and carries the rails; a bed segment overlapping a road by more than 0.5 m² is dropped. The gauge comes from the `gauge` tag (default 1435 mm). No sleepers and no rail sides: sides doubled the vertex count, and a stripe pattern shimmers on the GPU. Samples are at most 5 m apart; a 2 m step made the Stuttgart tiles 274 instead of 201 MB (178 MB without railways). Trees keep `RAIL_CLEAR` (3 m) from a drawn track. The `rails` layer has no collision: the car drives through bed and rails. Nothing else reads the rails, so gates and clipping counts stay exactly as without them. Stuttgart: 2286 ways, 393 km, 18 km as rails on a road, 12 km on bridges (`rails` in `metrics.json`); views in `godot/tools/viewpoints_rails_stuttgart.json`.

## Start points

`starts.json` lists the drive-menu starts. Each entry has `name`, optionally `road` (a named road within 300 m of the point wins over any other road), `at` as `[lat, lon]` and optionally `toward`; the point is snapped to the nearest drivable edge and the driving direction is the one closer to `toward`, without it the edge direction (effectively arbitrary). `route_start: true` takes the first route point and enables the lap timer. A start must lie on a drivable road with free space around it: an early route start on a car park of `service` ways, which the network does not contain, put the car on bare terrain and into a building. Take the midpoint of an edge from the extract for `at`; a coordinate from a map snaps tens of metres away. An edge without a name in the extract (a roundabout) is matched without `road`, because the name snaps to a different way.

## Testing

`make test W=<id>` runs the headless smoke test: settle the car on every start, move it 25 m off the road, roll it and check that F puts it back upright and, with `roads.bin`, within 1 m of the nearest road's centre line, then the world's own runs from `smoke.json` (`tunnel`, `bridge`: a steered drive along a fixed path that must reach the end, stay upright and not climb more than `rise_m`). A plain straight drive from a start does not exercise a portal (it stops short of it), and the car rolls on narrow ramps, so the runs are steered. The timing reference `godot/tests/reference_<id>.json` is written with `SMOKE_WRITE_REFERENCE=1`, only while `car.gd` is unchanged; the load time budget is `max(15 s, 1.25 × reference)`.

## Pack and ship

`pack.py` validates the manifest against `worlds/world.schema.json`, writes a ZIP (deflate, `world.json` first, tiles after) and a `.part` file that it removes on any error. The manifest adds `built`, `commit`, `size_bytes` and the SHA-256 of every file. `roads.bin` (the road centre lines, float32 x, y, z, edge per 5 m sample, y the drawn surface) is packaged with the tiles; the game uses it for F (`road_index.gd`, nearest segment in 3D), and an older package without it falls back to righting the car on the spot. Stuttgart: 175.6 MB unpacked, 56.6 MB packed; a ZIP costs about 10 to 15 % load time against a directory. The 500 MB limit per world is a project decision. `smoke.json` and the references stay in git and are not packaged. A world is self-contained and the launcher interface (`--world`, `--route`, `--start`) is stable.

## Working on a shared host

Before a download, build or render: `cat /proc/loadavg` (start below 4), `free -h` (more than 1 GiB free), run with `nice -n 19`, one heavy job at a time. Docker on the host cannot see `/tmp`: a world to render must live under the home directory. A git worktree for a branch has no `data/`; symlink `data/raw` from the main checkout instead of downloading again, and remember that removing a worktree deletes its ignored `data/` and `.venv`.
